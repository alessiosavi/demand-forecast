# Corpus v2

Corpus v2 adds 15 real-data configurations from `autogluon/chronos_datasets`
(revision `eeecad0b82a8c237e212ce6f8d1abecb513e2cec`) and 17 folders from
`Salesforce/GiftEvalPretrain` (revision `6830b624de7ed2b3d3e5b85bb6959d81dcc5d874`).
The existing `tsmixup` and `kernel_synth` shards remain separate kinds. Their
values, synthetic weekly loader coordinates, RNG seeds and legacy mixing
schedule are unchanged.

The exhaustive, offline-loadable recipe is
[`configs/corpus-v2.yaml`](https://github.com/alessiosavi/demand-forecast/blob/main/configs/corpus-v2.yaml).
It records every included source's licence, attribution, URL and bucket,
and every exclusion from the reviewed shortlist. The recipe and all nested
sections reject unknown keys.

## Contents and exclusions

Chronos includes electricity, exchange rates, car parts, COVID deaths, London
smart meters, river flow, weather, traffic, Wikipedia and wind farms. GiftEval
adds air quality, flu surveillance, household/building energy, disease counts,
solar/wind generation, Wikipedia and sunspots. Multivariate targets become
separate univariate component series.

Excluded groups are fev-task overlaps, the external validation dataset,
source-level duplicates, missing or unverified licences, and competition data
with unclear original grants. The owner excluded `weatherbench_*`. GiftEval's
remaining folders are excluded by one catch-all rule covering climate
simulations, cloud traces, PEMS/metro traffic, very large building collections,
and other unselected data. The exact names and reasons live in the YAML;
the converter downloads only its explicit include list. This screening is
**not a content-overlap audit**: value matching against fev tasks is a later task.

## Licence position

**`commercial_use: false`.** This is a research release. GiftEvalPretrain's
bundle-level research-only statement applies even when an original source
allows commercial use. `yes` denotes source-level commercial permission, `nc`
non-commercial source terms, and `sa` share-alike terms. These buckets do not
replace the original terms or imply clearance for commercial training.

TemperatureRain records both its original **CC BY-SA 3.0 AU** terms and the
collection card's **CC BY 4.0** label, under bucket `sa`. Building Data Genome 2
retains the licence-text inconsistency noted in the source research.

TSMixup / KernelSynth: generated by Amazon's Chronos authors from 28 public
datasets; no explicit licence on the dataset card; used under research terms.
The 28-source derivation refers to TSMixup; KernelSynth uses Gaussian-process
samples. This research-use declaration does not establish a new upstream grant.

See the [NOTICE-corpus.md attribution reference](NOTICE-corpus.md). Each build
also writes its own `NOTICE-corpus.md` beside `manifest.json`, containing only
that build's selected sources plus the synthetic-corpus statement. Keep that
file with the corpus when moving it.

## Build and verify

Install the optional conversion dependencies; ordinary model training does not
require the `datasets` package unless external dataset validation is enabled:

```bash
pip install -e '.[corpus]'
demand-forecast pretrain corpus build --config configs/corpus-v2.yaml --root /data/corpus
demand-forecast pretrain corpus verify --root /data/corpus
```

Preview every included remote file and byte size without downloading or creating
the root:

```bash
demand-forecast pretrain corpus build --config configs/corpus-v2.yaml \
  --root /data/corpus --dry-run
```

The pinned Hub file lists total **1,767,335,185 bytes** for Chronos real data and
**3,586,526,312 bytes** for GiftEvalPretrain (verified 2026-11-04). Allow additional
disk space for downloads, a SQLite sort/deduplication spool, staged output, and
any previous build during conversion. These figures exclude legacy synthetic
shards and the external validation set.

`--source chronos_real` or `--source gifteval_pretrain` selects a complete source;
the option is repeatable. A subset is a standalone build: use a fresh root or
rebuild all desired new kinds together. A subset build refuses existing
unselected new kinds, because independent builds cannot establish global
first-series deduplication order. Existing synthetic shards are preserved and
included in the refreshed manifest. This command does not download synthetic
shards or the external validation dataset. The existing Python
`download_shards` helper now defaults to the Chronos pin; explicit `revision=None`
retains the previous unpinned behavior.

Downloads go to `<root>/downloads/<source>` and are removed after success.
`--keep-downloads` retains them. For offline conversion, set a source's
`local_path` to a snapshot directory containing its config/folder subdirectories.
Relative local paths resolve against the recipe's directory. Local inputs are
marked as local in `corpus.json`; the declared revision is provenance, not a
verification that edited local files match the Hub. Local directories are never
deleted. A failed conversion leaves published shards unchanged; publishing
requires exclusive access to the root. Do not train or run concurrent builders
there while replacing a corpus.

## Conversion and reproducibility

Chronos parquet rows normally contain `id`, `timestamp`, and `target`.
The pinned card has three exceptions, recorded as `target_column` mappings:
`electricity_15min → consumption_kW`, `monash_saugeenday → T1`, and
`monash_temperature_rain → t_mean`. Other weather/covariate columns are ignored.
GiftEval folders are saved Hugging Face datasets with `data-*.arrow`,
`dataset_info.json`, and `state.json`; the converter reads `item_id`, `start`,
`freq`, and `target` only. A nested target is component-major, with IDs ending in
`/<dim>` (zero-based). Missing values stay NaN.

Rows are sorted by source name, folder/config name, string item ID, and numeric
component index. Filters run in this order, counted per folder:

1. Drop all-NaN targets.
2. Drop targets with fewer than 64 finite values (configurable).
3. Drop targets with at most one distinct finite value.
4. Deduplicate across all selected new kinds using SHA-256 of little-endian
   float32 value bytes, with NaN signs/payloads canonicalized. Keep the first
   candidate in the defined order; timestamps and IDs do not affect this hash.
5. Optionally cap each folder: select the lowest SHA-256 priorities seeded by
   folder name, item ID and component, then restore sorted output order.

The cap defaults to off. Deduplication precedes the cap, so a duplicate-pair
representative may itself later be subsampled out. Signed zero and infinities
retain their float32 bytes; only finite values count toward eligibility. The
legacy synthetic corpus does not participate in this new-kind deduplication.

Conversion streams one input row at a time and uses a disk-backed SQLite sort
and hash index. The writer retains at most one bounded shard buffer, apart from
individual long rows and encoding buffers. Shards have at most 20,000 series
and 256 MiB of actual parquet bytes. A single series exceeding the byte limit
fails with its ID; it is not silently truncated. Final filenames are
`training_corpus/<kind>/train-XXXXX-of-NNNNN.parquet`.

Output columns are `id`, `target: list<float32>`, `start: timestamp[ns]`, `freq`,
`source`, and `folder`. GiftEval rows carry the source's own alias, Chronos rows
pandas' inferred alias at build time; aliases are not normalised — consumers map
them to frequency classes. If pandas cannot infer a Chronos frequency and at
least two timestamps exist, the converter uses the modal positive timestamp
delta (ties choose the smallest), converted to pandas' offset alias.
Non-monotonic timestamps or no positive delta fail with the series ID.
`freq_fallback` counts series using this fallback before filtering, per folder
and in source/corpus totals, alongside the dropped counters.
The training loader still reads only
`id` and `target`, using its synthetic weekly grid. Source start/frequency are
retained for later calendar-aware work.

Pinned revisions, deterministic order and fixed PyArrow settings (Parquet 2.6,
Zstd level 3, 1,024-row groups, no dictionary encoding) make repeated conversion
from the same downloads byte-identical in fixture tests. Cross-platform byte
identity is expected but verified only by comparing manifest hashes; library
or codec version changes can change encoded bytes. `verify` rehashes every
manifest shard and exits 1 on a missing file, wrong size or changed digest,
printing one summary per kind.

Alongside the shards, builds write:

- `manifest.json`: the existing portable list of root-relative path, kind,
  index, SHA-256 and byte size, including any existing legacy shards.
- `corpus.json`: recipe SHA-256, build-tool version, `pandas_version`,
  `pyarrow_version`, `commercial_use`, filter and
  shard settings; source repo/revision/kind/bundle terms/input mode; per-folder
  attribution and series/point/filter counts; source and corpus totals.
  `points_kept` counts positions including missing values; `finite_points_kept`
  counts finite observations.
- `duplicates.jsonl`: ordered `{kept_id, dropped_id}` records, linked from
  `corpus.json`, so duplicate reporting does not accumulate in memory.
- `NOTICE-corpus.md`: source attributions, licence URLs and research terms.

The manifest verifies shard bytes, not legal clearance, upstream authenticity
of local overrides, or fev content isolation.

## Training with weighted sources

`configs/corpus-v2.yaml` is a build recipe. A pretraining run uses a separate
`PretrainConfig`, for example this `corpus` section (choose indices from your
own build's manifest):

```yaml
corpus:
  root: /data/corpus
  sources:
    tsmixup: {shards: [0, 1], holdout: [199], weight: 8}
    kernel_synth: {shards: [0], holdout: [19], weight: 1}
    chronos_real: {shards: [0], holdout: [1], weight: 2}
    gifteval_pretrain: {shards: [0], holdout: [1], weight: 2}
  val_pairs_per_kind: 4096
  external_validation: monash_nn5_weekly
```

Each source requires nonempty training shards, disjoint hold-outs and a finite
positive weight. `tsmixup` is required for the model specification. Adding
another registered kind only requires another mapping entry and its local
manifest shards. New converter kinds additionally need a registry path, stable
RNG kind code and input adapter. Never renumber existing kind codes.

Weighted mixing uses **smooth weighted round-robin**. Each step adds each kind's
weight to its credit, picks the largest credit, then subtracts the total weight
from the winner. Ties use stable kind order: TSMixup, KernelSynth, Chronos real,
GiftEval. Decimal weights become exact integers. A checkpoint stores credits,
weights and all stream positions, so resuming preserves kind and batch order.

Without `sources`, the old zero-based `kernel_synth_every` schedule, config dump
and run identity are unchanged. With `sources`, omit legacy shard/mixing fields;
explicit legacy shard/hold-out lists must agree. An explicit
`kernel_synth_every` is accepted only for a matching two-kind weight ratio (or
zero for TSMixup alone); weighted mode still uses round-robin ordering.

Only the arithmetic mean of the TSMixup and KernelSynth hold-out SQL scores
selects a model. Supply both legacy hold-out kinds for a finite selection score;
a missing score still makes the selection mean NaN, as before. New-kind scores
appear as `val_sql_chronos_real` / `val_sql_gifteval_pretrain` diagnostics.
The local `monash_nn5_weekly` external diagnostic is unchanged.
